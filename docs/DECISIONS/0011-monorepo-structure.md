# ADR 0011: Monorepo via npm workspaces + uv

**Status:** Accepted
**Date:** 2026-05-16

## Context

The project has two services (Next.js frontend, FastAPI backend) plus shared TypeScript types. Three structural options:

- **Two separate Git repos** — one for `web`, one for `api`. Independent deploys, clean isolation.
- **Monorepo with a heavy tool** — Turborepo, Nx, Rush, Lerna. Designed for large multi-team monorepos.
- **Monorepo with light tooling** — npm workspaces for JS, uv for Python, no orchestrator.

## Decision

Single Git repo with this top-level layout:

```
img-vid-generation/
├── apps/
│   ├── web/        # Next.js (npm workspace member)
│   └── api/        # FastAPI (uv-managed Python project)
├── packages/
│   └── shared-types/   # Generated TS types from FastAPI's OpenAPI
├── docs/
├── docker-compose.yml
├── package.json    # npm workspaces root
└── .claude/
```

- **JavaScript side:** npm workspaces. Root `package.json` declares `"workspaces": ["apps/web", "packages/*"]`. No Turborepo — it adds value at multi-team scale, not here.
- **Python side:** uv is project-local to `apps/api/`. Python and JS dependency systems do not need to know about each other.
- **Coordination scripts** in root `package.json`: `dev:web`, `dev:api`, `dev:worker`, `dev` (all three concurrently via `npm-run-all` or `concurrently`).

## Consequences

**Positive:**
- Single git history for the product. Atomic PRs across frontend and backend are possible (and common — adding an API endpoint plus its UI is one logical change).
- `docs/` and ADRs live once, not twice.
- Generated types in `packages/shared-types` are committed to the repo and consumed by `apps/web` as a workspace dependency — no publish step.
- One CI pipeline can lint/test/build both services.
- Cloning a single repo gets a new contributor (or future-me on a new machine) the entire system.

**Negative:**
- Deploys must filter by changed paths to avoid redeploying the unchanged service. Both Vercel and Cloud Build support this; it's a configuration concern, not a blocker.
- Mixing Python and JS tooling in one repo means contributors need both `node` and `python` installed.
- Some IDEs (less of an issue in modern VS Code) treat the root differently from per-service roots.

## Alternatives considered

- **Two repos.** Considered. Rejected because cross-cutting changes (a new endpoint + its UI) become two PRs, two reviews, ordering risk. For a solo developer this overhead is pure cost.
- **Turborepo / Nx.** Rejected. They shine at 10+ packages and multi-team contention. Two apps and one package does not justify the configuration overhead.
- **Single language only.** Rejected — chose FastAPI explicitly in ADR-0007.

## Implementation notes

- Root `package.json` script naming: `dev:*` for development, `gen:api-types` for OpenAPI codegen, `lint:*` per workspace.
- `packages/shared-types/api.d.ts` is regenerated by `npm run gen:api-types` (which spins up the FastAPI dev server transiently or hits a running one). Committed to git so frontend builds work without FastAPI running.
- Each app keeps its own `.env` and `.env.example`. No shared `.env` at the root to avoid polluting unrelated services.
- `docker-compose.yml` at the root manages local infrastructure (Redis now; could grow to include Postgres if Supabase becomes a constraint).
