# ADR 0007: FastAPI as a separate backend service

**Status:** Accepted
**Date:** 2026-05-16

## Context

The original plan was a Next.js monolith with Server Actions handling all backend work. After review, the user raised legitimate concerns:

- **Framework coupling.** Server Actions are a Next.js convention; business logic tied to them is hard to extract.
- **No first-class background workers.** Cron, queues, retries require bolt-on solutions.
- **Webhook reliability.** Stripe webhook handling needs durable execution.
- **Coupled deploy lifecycle.** Frontend tweaks force backend redeploys.
- **No path to other clients.** Mobile app or partner API can't consume Server Actions.

The user also wants to learn Python and FastAPI specifically, and the AI/ML Python ecosystem (Gemini SDK, future custom embeddings) is materially better-maintained.

## Decision

Split into two services in a monorepo:
- **`apps/web`** — Next.js handles UI, OAuth flow (Auth.js), thin reads. Does not access the database directly.
- **`apps/api`** — FastAPI owns the database, AI orchestration, jobs, webhooks, business logic.

Communication: REST over HTTPS, JWT auth (ADR-0009). Contract: OpenAPI auto-generated by FastAPI, TS types codegen'd into `packages/shared-types`.

## Consequences

**Positive:**
- Clean service boundaries — each side can evolve independently
- Backend can be deployed and scaled differently from the frontend (e.g., Celery workers on Cloud Run, Next.js on Vercel)
- Python ecosystem advantages: official Gemini SDK is Python-first, future ML work (embeddings, fine-tuning) is natural
- Backend is reusable by future mobile apps or partner integrations
- Concrete learning value: REST design, JWT auth across services, OpenAPI codegen, Python async, Celery
- FastAPI's auto-generated OpenAPI + `openapi-typescript` gives near-tRPC type safety across the language boundary

**Negative:**
- Two services to develop, two to deploy, two to monitor
- Local dev requires running both processes (mitigated by `npm run dev` orchestration)
- CORS / network configuration needed
- Auth.js types are TS-only — the Python backend can't share session types directly (mitigated by JWT being a public contract)

## Alternatives considered

- **Pure Next.js monolith with Server Actions.** Rejected because of the framework coupling and lack of native job queue support. The architecture would have required bolt-on tools (Inngest, BullMQ) that essentially recreate what FastAPI + Celery does natively.
- **Modular monolith.** Considered. Would have deferred the split, but the user's explicit goal is to *learn* a separate backend, and deferring removes that learning.
- **Hono + Bun separate backend.** Strong contender. Rejected because the user specifically wants to return to Python and learn FastAPI.
- **Go backend.** Considered for maximum learning. Rejected because Python's AI ecosystem advantage was the deciding factor for this specific product.
